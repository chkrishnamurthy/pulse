Step 1 · Know the options

The four Google health APIs, and which ones are still alive

You will find many tutorials online. Most are now out of date. Here is the real status today.

✔ Use this

Google Health API

New cloud API at health.googleapis.com/v4. Reads all your Fitbit data from Google's servers: steps, heart rate, sleep stages, SpO2, workouts and more. Uses normal Google sign-in (OAuth 2.0).

✖ Turned off

Fitbit Web API (old)

The classic api.fitbit.com API. Support ended 30 Sep 2026 and it was switched off on 2 Nov 2026. Any tutorial using it will fail.

✖ Being shut down

Google Fit API

Old Google fitness API. Deprecated, no new sign-ups, and support ends in 2026. Google tells developers to move to Google Health API or Health Connect.

◐ Helper only

Health Connect

A store on your phone, not in the cloud. Apps share data through it. The Fitbit / Google Health app can copy some data into it. Good as a backup source, but it has fewer Fitbit details.

Step 2 · Understand the journey

How your Fitbit data reaches your app

Your tracker never talks to your app directly. It always goes through Google first. Your app reads it from Google.

Important: data only appears after the tracker syncs.If your tracker has not synced to the phone, the API has nothing new. The API is never "live from the wrist". This is normal and our app must show "last synced at …".
One setup step before any code.Google says you must first link Google Health to your Google account inside the Google Health app. If not, the API returns error ACCOUNT_NOT_LINKED.

Step 5 · Rules and limits

Can a personal app read my own data? Yes. Here are the rules.

Approval

No review needed for personal use

New apps start "unverified" with a cap of 100 users. You are 1 user, so this is fine. A security review is only needed if you go above 100 users. No special access form is needed.

Catch

"Testing" mode logs you out every 7 days

In Testing mode, refresh tokens expire after 7 days. You would need to sign in again each week. In "In production" mode, refresh tokens normally last until unused for about 6 months. We will choose this in Phase 2.

Cost

Free, with generous limits

Google Cloud project is free. Limits are far above what one person needs. No sandbox exists, so we test with your real data.

Rate limits (from Google)

Per user, per minute
300

~20

A full refresh of one day needs about 15–20 calls. A one-time history download needs more, so we will go slowly and retry on error 429.

Step 6 · The design

Recommended architecture

We build in two stages. Stage A is a phone-only app (simple, no server). Stage B adds a tiny server only if we want instant push updates and the strongest token safety.

Why phone-only first?

Fewer moving parts for a beginner. No server to pay for or secure. Your data stays between your phone and Google. Good enough for one person.

Why add a server later?

Only a server can receive Google's push messages (webhooks), keep a long-life refresh token fully off the phone, and sync while your phone is off.

Why a local database?

The dashboard opens instantly and works offline. Each record is saved by its unique id, so syncing twice never creates duplicates.

Step 9 · Stay safe

Security and privacy rules we will follow

No secrets in the app

An Android app can be unpacked by anyone. We never put a client secret or API key in it. Android sign-in uses your app's package name and signing fingerprint instead.

Tokens stay locked

Access tokens live in memory (they last about 1 hour). Anything kept on disk is encrypted with Android Keystore. In Stage B the refresh token lives only on the server, in Secret Manager.

Health data is private

Room database is encrypted, excluded from cloud backup, and never logged. We ask only for read-only scopes. Server calls use HTTPS and check Google's webhook signature.
